# Plugin Development

Use this guide to build or update a Dataiku plugin. First check whether a built-in
Dataiku feature or an existing [store plugin](./administration/plugins.md#store-discovery)
meets the need. For installation, updates, removal, and code
environment setup, follow [Plugins](./administration/plugins.md).

## Before You Start

Work in a local checkout. Headless can upload the finished package over stdio or
install or update it from a Git repository over either transport. It cannot create a
development plugin or edit its files on the instance.

Read the repository instructions, `plugin.json`, and the code and descriptors for
the components you will change. Check dependencies, packaging commands, and tests.
Preserve IDs, role names, and configuration keys that existing usages depend on;
explain how users should migrate if you need to change them.

For a new plugin, identify its purpose, ID, Dataiku version, and local folder. Choose
a test instance before installation. Start from a template the user supplies or the
[official component tutorials](https://developer.dataiku.com/latest/tutorials/plugins/index.html)
for that Dataiku version. You do not need Dataiku's internal templates or infrastructure.

The plugin code can use documented Dataiku APIs. To change the instance, use
Headless tools; to build project assets, use [Cobuild](./cobuild.md). If the tools
cannot perform a needed step, explain what must be done in the UI rather than
working around the gap with SDK or REST calls.

## Writing The Plugin

- Set the plugin ID, version, and display information in `plugin.json`. Define each
  component's parameters in its descriptor, with clear descriptions of what it does,
  what inputs it needs, and what it returns.
- Keep component entry points short and put shared logic in `python-lib/`, which
  Dataiku adds to the Python path. Where practical, keep that logic independent of
  Dataiku so you can test it locally.
- Keep component settings separate from plugin-wide `plugin_config`. Use configured
  connections or [parameter sets](./plugin-development/settings-checks.md#parameter-sets)
  for credentials. Users enter actual secrets and preset values in the UI.
- Set `mandatory` explicitly and choose defaults that make sense for the component.
  Validate inputs in the code as well as the UI. Write `visibilityCondition` in
  JavaScript using `model` to access parameter values.
- Use named loggers and record only the trace fields you need. Keep credentials,
  whole configuration objects, request headers, and sensitive results out of logs
  and traces. Remove sensitive details from errors shown to users.
- Define a plugin-managed Python environment in `code-env/python/desc.json` and
  `code-env/python/spec/requirements.txt`. Check that its interpreter and packages
  work with the intended Dataiku version and component. Visual ML extensions may
  run in the model's training or scoring environment instead. A root
  `requirements.json` only describes dependencies; it does not install them.

See [parameters](https://doc.dataiku.com/dss/latest/plugins/reference/params.html)
and [dependencies and shared libraries](https://doc.dataiku.com/dss/latest/plugins/reference/other.html).

## Test And Package

1. Run the repository's documented tests, using fakes for external services and
   Dataiku APIs. Check invalid inputs, empty results, failures, and whether outputs
   serialize correctly. Each component reference lists any additional checks.
2. Read the packaging command before running it. For example, `git archive HEAD`
   leaves out uncommitted changes. Check that the package contains your intended
   changes and follow the repository's release process.
3. Inspect the files in the ZIP. Include the code, resources, and built frontend
   assets the plugin needs. Leave out credentials, `.env`, local configuration,
   virtual environments, caches, and unrelated test data. Prefer a checked ZIP:
   directory uploads only skip `.git` and `__pycache__`.

## Deploy And Verify

Follow [Plugins](./administration/plugins.md) to install or update the package and
prepare its environment on the test instance. If the changes are already in a
remote repository, follow that guide's Git workflow to deploy the chosen revision.
The installed package is not an
editable development plugin. Use the UI for any required reload or restart.

Set up the test project through Cobuild, then run existing recipes or scenarios
with the execution tools. Use the UI where needed. Test the installed component and
inspect its results, following its reference. Keep run IDs so you can follow up
through [Jobs](./jobs.md). Report the package revision, test instance, results, and
anything still untested or requiring UI setup. Installation alone does not show
that the component works.
