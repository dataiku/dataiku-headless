# Dataiku Govern — Custom Pages

Govern's **Custom Pages** feature lets administrators define their own pages in the Govern UI. Use them to surface artifact dashboards, embed external tools (via iframe), or build custom kanban/matrix views over governed items.

This is the canonical mechanism for **embedding external content** (chat assistants, dashboards, BI tools, internal apps) inside the Govern UI without writing a plugin.

> **Boundary**: this doc covers the four built-in custom page **types** and how to author them. For the CLI commands that create/list/edit them, see `dku govern custom-page` in `references/govern.md`.

---

## The four custom page types

Govern ships four built-in custom page types. Each maps to an Angular component under `gh/server/frontend/projects/gh-frontend/src/app/custom-pages/` in the Govern source tree.

| Type | Component | What it shows |
|---|---|---|
| `custom-page-artifact-table` | tabular view | Table of artifacts matching a filter, with sortable columns |
| `custom-page-artifact-matrix` | matrix view | Two-dimensional grid of artifacts (e.g. status × team) |
| `custom-page-kanban-view` | kanban board | Cards grouped by workflow step, drag-and-drop transitions |
| `custom-page-custom-html` | raw HTML | **Anything you want** — arbitrary HTML, including `<iframe>` and `<script>` |

The first three are structured views over artifacts (you configure filters, columns, grouping). The fourth (`custom-page-custom-html`) is the escape hatch — it accepts any HTML and is the only way to embed content from outside Govern.

## Embedding external content with `custom-page-custom-html`

`custom-page-custom-html` is the page type you want when you need to put **anything** in front of users that Govern doesn't natively support: a chat assistant iframe, a Grafana dashboard, an internal tool, a Streamlit app, a Tableau view, etc.

### How it works

The component is implemented at:

```
gh/server/frontend/projects/gh-frontend/src/app/custom-pages/custom-page-custom-html/custom-page-custom-html.component.ts
```

The implementation is a few lines of Angular: it takes the `htmlContent` field from the page definition, runs it through `DomSanitizer.bypassSecurityTrustHtml(...)`, and renders the result inside a `mat-card`. From the source comment:

> *"Bypassing the security allows to use `iframe` elements. The drawback is that it also allows `script` elements but it is safe here because the `htmlContent` field is editable ONLY by the administrator."*

So **iframes and scripts are both allowed** — Govern is trusting the admin to author safe content. The content is wrapped in a Material card that takes 100% width and height of its container, with `overflow: auto`.

### Authoring a custom-html page

1. **In the Govern UI**: go to **Custom Pages** → **+ New Custom Page** → pick **Custom HTML**, give it a title, paste your HTML into the content editor, save.
2. **Via the CLI**: `dku govern custom-page create <id> --definition @page.json`. The definition has the shape:

   ```json
   {
     "id": "cp.my_page",
     "name": "My Page",
     "type": "custom-html",
     "htmlContent": "<div>... your HTML here ...</div>"
   }
   ```

   Use `dku govern custom-page get <id> -o json` on an existing custom-html page to see the full shape.

### Recipe: embed an iframe full-viewport

The most common use case — embed an external app (a chat assistant, a dashboard, a webapp from another DSS instance) so that it fills the entire custom-page area:

```html
<style>
  /* Govern wraps custom HTML in a mat-card with overflow:auto.
     We take 100% of its space and let the iframe own its own scrolling. */
  .embedded-app {
    position: absolute;
    inset: 0;
    width: 100%;
    height: 100%;
    border: 0;
    margin: 0;
    padding: 0;
  }
</style>

<iframe
  class="embedded-app"
  src="http://your-tool.example.com/?param=value"
  title="My embedded tool"
  allow="clipboard-read; clipboard-write"
  referrerpolicy="no-referrer-when-downgrade">
</iframe>
```

### Recipe: embed a DSS Standard Webapp

If you've built a Standard Webapp on a DSS instance and want to surface it inside Govern (this is a common pattern — DSS holds the data + business logic, Govern is the user-facing surface), use the **bare webapp view URL**, not the DSS Angular shell URL.

The two URLs serve very different things:

| URL pattern | What it serves |
|---|---|
| `http://<dss>/projects/<PROJECT>/webapps/<id>_<slug>/` | DSS Angular SPA shell with project sidebar, top nav, etc. **Do not iframe this.** |
| `http://<dss>/webapps/<PROJECT>/<id>/` | The bare webapp view — just the webapp's own HTML/CSS/JS, no DSS chrome. **Use this for iframes.** |

The bare-view path is auto-generated by DSS in its nginx config (it's the `/webapps/<proj>/<id>/` location block, which rewrites to the internal `/dip/api/webapps/view?projectKey=...&webAppId=...` view).

So a Govern Custom HTML page that embeds a DSS webapp at id `JlRVazf` in project `MY_PROJECT` looks like:

```html
<style>
  .webapp-embed {
    position: absolute; inset: 0; width: 100%; height: 100%;
    border: 0; margin: 0; padding: 0;
  }
</style>
<iframe
  class="webapp-embed"
  src="http://localhost:8082/webapps/MY_PROJECT/JlRVazf/?project_id=MY_PROJECT"
  title="My DSS webapp"
  allow="clipboard-read; clipboard-write">
</iframe>
```

Replace `localhost:8082` with whatever URL the user's browser uses to reach DSS (not the URL the Govern server uses internally).

### Cookies, auth, and same-site behavior

If Govern runs on `localhost:8102` and DSS runs on `localhost:8082`, browsers treat them as **same site** (both `localhost`) but different origins. Practical implications:

- **Cookies are sent** in the iframe request because `SameSite=Lax` (the DSS default) allows same-site iframe requests. The user just needs an active DSS session in the same browser.
- **CORS does not apply** to iframes loading HTML — only to fetch/XHR requests across origins. The iframe's own JS calling its own backend is same-origin, so no CORS preflights either.
- For **production deployments** where Govern and DSS are on different hosts (e.g. `govern.acme.com` vs `dss.acme.com`), the same-site rule still applies if both share a registrable domain (`acme.com`). If they're on truly different domains, the user needs to be logged into both, and you may need to switch the DSS webapp to public access mode.
- For **anonymous (no DSS login) embedding**, set the webapp's `forceAuthentication` flag to `false` and use the `/public-webapps/<proj>/<id>/` path instead. Be aware this exposes the webapp's backend to anyone who can reach the URL.

### Passing context from Govern to the embedded app

The simplest way to pass context (current artifact id, blueprint id, project key) from Govern to your iframe is **URL parameters** appended to the `src`. The embedded app reads `window.location.search` and uses the values.

```html
<iframe src="http://localhost:8082/webapps/MY_PROJECT/JlRVazf/?artifact_id=ar.42&blueprint_id=bp.foo">
</iframe>
```

This works when the context is **static** (the page is configured for one specific artifact). If the context needs to be **dynamic** (the iframe should react to the user navigating inside Govern), you'd need either:

1. A small `<script>` in the custom HTML page that reads the current Govern route and rebuilds the iframe `src`, OR
2. `window.postMessage` from the parent (your custom HTML page) to the iframe, with a listener inside the embedded app

For most embedding scenarios the static URL-parameter approach is enough — you're embedding a tool that operates over the whole project, not a tool that follows the user around the Govern UI.

## Security notes

- `htmlContent` accepts arbitrary HTML and JavaScript. **Only Govern administrators can edit it** — Govern enforces this in the UI and via the `dku govern custom-page set-definition` API call. Don't expose this endpoint to non-admin users.
- Embedded iframes inherit the user's cookies for any same-site origins. If you embed a tool that serves sensitive data, that tool must enforce its own auth.
- `<script>` tags in `htmlContent` execute with the same privileges as Govern's own frontend. Don't load scripts from untrusted CDNs.
- For embedded content from third parties, consider setting a CSP `frame-ancestors` directive on the embedded app's response so it can only be iframed by your specific Govern host.

## When NOT to use a Custom HTML page

- **You need a structured artifact view (table, matrix, kanban)** — use the corresponding built-in custom page type instead. They get filters, sorting, and Govern's standard styling for free.
- **You need to write a plugin** — Custom HTML pages are admin-edited content, not deployable artifacts. If you want something installable across many Govern instances with versioning and code, build a Govern plugin.
- **You need bidirectional Govern ↔ external tool integration with rich state** — `postMessage` over an iframe boundary is workable but limited. For deep integration, write a Govern plugin that uses Govern's own component API.
